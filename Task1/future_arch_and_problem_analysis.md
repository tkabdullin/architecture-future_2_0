# Задание 1. Видение будущей архитектуры, анализ проблем и их приоритезация

## C4 Container Diagram будущей архитектуры
Будущая архитектуры систем компании должна состоять из следующих компонент через 1 год (предположительно):

 - Integration Bus
   - Apache Camel остаётся в качестве Enterprise Service Bus (ESB), выполняя функции маршрутизации, трансформации, оркестрации и интеграции между backend-сервисами.
   - Camel принимает события от финансовых и медицинских систем, а также от внешних API, и направляет их в Kafka.
 - Event Streaming Platform
   - Apache Kafka используется как шина потоковых данных.
   - Camel публикует события в Kafka, а downstream-системы (например, DWH и AI) читают их для обработки и хранения.
   - Kafka дополняет, а не заменяет ESB, позволяя реализовать event-driven архитектуру.
 - Data Platform
   - Новый Data Warehouse (Hadoop, Spark) заменяет устаревшее хранилище в части актуальных данных. Он построен на:
 - Data Lake (HDFS) — хранение необработанных и разнородных данных.
 - Data Marts (Hive) — специализированные витрины данных для BI и AI.
 - Legacy DWH (PostgreSQL/Oracle) сохраняется в режиме "только для чтения" для доступа к историческим данным.
 - BI Platform
   - Tableau / Metabase предоставляют пользователям мощные инструменты самообслуживания (Self-Service BI).
   - BI-платформа подключается как к актуальным витринам (Hive), так и к архивному хранилищу (Legacy DWH).
 - AI Platform
   - Специализированная платформа для ИИ, построенная на Python и ClickHouse.
   - Использует данные из Data Marts для аналитики и обучения моделей.
   - Взаимодействует с пользователями через отдельное React Native приложение.
 - API Gateway
   - Единая точка доступа ко всем backend-сервисам: KrakenD обеспечивает маршрутизацию, авторизацию и консолидацию API для всех frontend-приложений.
 - Keycloak (IdP)
   - Единый центр аутентификации и авторизации всех пользователей: клиентов, врачей, администраторов.
 - Интеграция с внешними системами
   - Системы лабораторной диагностики (LIS) и аптечного управления (Pharma) подключены к медицинскому API Gateway через HTTPS.

### Описание будущей архитектуры
Компания «Будущее 2.0» планирует масштабную модернизацию своей ИТ-инфраструктуры, реализуя отказ от устаревших решений и переход к современной, модульной и потоково-ориентированной архитектуре. Целью трансформации является повышение гибкости, масштабируемости и скорости принятия решений на основе данных.

<b>Основные изменения:</b>
 - Разделение на функциональные домены
   - Вся система структурирована по доменам: финтех, медицина, искусственный интеллект, аналитика.
   - Каждый домен имеет собственный backend, frontend и БД.
   - Централизация через общие компоненты: шина данных, DWH, BI и идентификация.
- Сохранение интеграционной шины Apache Camel
  - Вместо замены, Camel продолжает использоваться как ESB.
    - Он маршрутизирует, трансформирует и оркеструет данные между backend-сервисами.
   - Принимает события от медицинской и финтех-систем, а также внешних API (через внутренний gateway).
   - Camel публикует данные в Kafka, обеспечивая совместимость с новой event-driven архитектурой.
 - Переход к потоковой передаче данных с Apache Kafka
   - Kafka используется как event streaming-платформа.
   - Консьюмеры (например, модуль загрузки данных в DWH) читают события для последующей обработки.
 - Модернизация DWH
   - Введён новый DWH на базе Hadoop/Spark:
   - Хранение данных — в Data Lake (HDFS).
   - Бизнес-ориентированные витрины — в Data Marts (Hive).
   - Историческое хранилище (Legacy DWH) остаётся в режиме только для чтения и используется для архивной отчётности.
 - Витрина данных и BI-платформа
   - BI-платформа (Tableau, Metabase) подключается как к новым витринам (Hive), так и к старому DWH.
   - Поддержка self-service BI: врачи, клиенты и администраторы получают доступ к отчётам через личные кабинеты.
 - Платформа ИИ
   - Отдельный backend на Python, БД на ClickHouse.
   - Использует агрегированные данные из Data Marts для аналитики и обучения моделей.
   - Клиенты и врачи взаимодействуют с платформой через собственное приложение.
 - API Gateway и идентификация
   - KrakenD обеспечивает централизованный доступ к сервисам.
   - Keycloak выполняет функции аутентификации и авторизации для всех типов пользователей.
 - Интеграция с внешними бизнесами
   - Медицинский gateway предоставляет API для подключения внешних систем:
   - LIS — лабораторные информационные системы.
   - Pharma — аптечные и складские системы.

## Проблемные места и их приоритизация
|Проблема|Описание|Приоритет|
|-|-|-|
|Устаревший DWH|SQL Server 2008 не масштабируется, сложен в обслуживании|must have|
|Медленные отчёты|Встроенная бизнес-логика замедляет построение аналитики|must have|
|Отсутствие модульности|Новые бизнесы требуют изменений в центральной системе|must have|
|Устаревшая шина данных|Apache Camel не поддерживает современные требования к интеграции|nice to have|
|Нет удобного BI-решения|Требуется гибкий инструмент самообслуживания|nice to have|
|Неэффективное хранение данных|Всё хранится в одном DWH, нагрузка растёт|nice to have|
